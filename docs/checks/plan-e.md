# Plan E: what ran, and what to check by hand

The run was on the `plan-e` branch, on a 16-core Linux laptop, with Rust 1.98.0, on 2026-11-23 and 2026-11-24. The branch hasn't been pushed or merged. **Nothing here has run on Windows. The Windows build of the app, the helper, the console twin, `scripts/package-windows.ps1`, `scripts/test-all.ps1` and the Inno Setup script have never been compiled or run; the Windows target can't be installed on this machine.** The Windows files are checked only by tests that read them as text.

## What was built

One per-user package for each system, and one script per system that runs every test. Both packages hold the app, the compiler bundle, the live terminal's helper (`stagepack-terminal`, off until a talk asks for a command and you say yes), the AI tool's guide, the fonts, the icon and every licence notice.

- **`crates/xtask`** (binary `package`), dev-only: `package icon` draws the app's icon in code (a rounded square in the accent colour with a white slide and a small play triangle) as PNGs from 16 to 512 pixels and an `.ico`; `package notices` writes `NOTICES.txt` from `cargo metadata` (every crate in the app's and the helper's graph for Linux and Windows x86_64, with licence expression and text, the fonts, the Rust and LLVM notices from the toolchain, OpenH264) and fails if a crate has neither a licence file nor an expression; `package stage` builds the installed folder from release builds and the compiler bundle and fails above 600 MB; `package windows-folder` stages the Windows folder (on a Windows PC); `package linux` packs the Linux `.tar.zst`.
- **A `shipped` feature** of the app: such a build ignores `STUDIO_BUNDLE` and `STUDIO_TERMINAL_HELPER` and looks beside its own executable only. On Windows a shipped build has two programs: `stagepack-studio.exe` (no console window; double-click and the file type use it) and `stagepack-studio.com` (a console twin that waits and keeps the exit code, so commands and an AI tool's MCP server work in a terminal).
- **Linux:** `stagepack-studio-0.1.0-linux-x86_64.tar.zst` with `install.sh`, `uninstall.sh` and `paths.sh`. Installs under the user's home only: `~/.local/lib/stagepack-studio`, a link in `~/.local/bin`, the menu entry, the `application/vnd.stagepack.talk` type (`*.sptx`, a subclass of zip, at the default glob weight, 50: where Stagepack is installed its weight-90 glob decides the type, so the file stays `application/x-stagepack` and both programs are offered for it) and the icons. Our entry lists both our type and `application/x-stagepack`, the type Stagepack registers for the same files, and becomes the default for both, so a `.sptx` opens in Stagepack Studio whichever type it is taken for; another program stays under *Open with*, and uninstalling puts back the default each type had in each `mimeapps.list` (recorded per type at the first install) if that program is still installed. Before the swap `install.sh` runs the new copy's `help`, and refuses with the loader's own message if it can't start (it needs glibc 2.35 or later, `libxkbcommon`, `libxkbcommon-x11`, `libxcb` and `libstdc++`). Since plan E2 the package is built by `scripts/package-linux.sh` in an Ubuntu 22.04 container, so it runs on Ubuntu 22.04, Debian 12 or newer. It refuses an unset or `/` home, relative or outside-home `XDG_*` values, anything in the app's data folder, symlinks and files that aren't ours; an upgrade replaces the folder atomically; uninstalling takes only what is ours and never touches `~/.local/share/stagepack-studio`.
- **Windows:** `packaging/windows/stagepack-studio.iss` (Inno Setup 6.3 or newer, `PrivilegesRequired=lowest`, `HKCU` only, ProgID `StagepackStudio.Talk` added to `.sptx\OpenWithProgids` without removing others, and the earlier default's ProgID added there too and kept after uninstalling; since plan E2 a `[Code]` section saves that earlier default in `HKCU\Software\Stagepack Studio` (`PreviousSptxDefault`, never our own ProgID, so an upgrade keeps it) and makes it the default again on uninstall if `.sptx` has none and the program is still installed, and adds `{app}` once to the user `Path` (`REG_EXPAND_SZ`, `ChangesEnvironment=yes`), taking only that entry off again on uninstall; an upgrade first removes the old `{app}\bundle`; the programs are built with the C runtime linked in; `%APPDATA%\stagepack-studio` never touched) and `scripts/package-windows.ps1`, which runs `test-all.ps1 -Quick`, stages the folder and runs `ISCC`.
- **Scripts that run every test** (this task): `scripts/test-all.sh` and `scripts/test-all.ps1` run, in order, *clippy*, *workspace* (all tests), *components* (the tests that need the compiler bundle, via `scripts/test-components.sh` or its new twin `scripts/test-components.ps1`), *release* (the timing tests, which only mean something in a release build) and *packaging* (the xtask's tests, including the two slow ignored ones). A failed step doesn't stop the next; the summary lists every step as ok or FAILED and the script exits 1 if any failed. A step that fails on tests is rerun once on those tests alone (a loaded machine fails timing tests), and both results are printed. `--quick` / `-Quick` skips the release step and the two slow packaging tests; `--list` / `-List` prints the steps; `--only STEP` (shell only) runs one. The README has *Install* and *Build the packages* sections.
- `scripts/test-components.sh` no longer runs `--ignored` over the whole workspace (which ran every timing test in a debug build, where they fail, and, once, the 300 MB-file tests); it runs the tests marked *needs the compiler bundle* and the AI tool's permitted build.

## Not done, and for the owner

These were found in review or while building and left, by ruling, as not blocking.

- **Questions for you:**
  - **Should the Windows installer add the app's folder to your user `PATH`?** *Answered (plan E2): yes.* The installer's `[Code]` adds `{app}` to the user `Path` once (compared without case and without a trailing `\`), written back as `REG_EXPAND_SZ`, and uninstalling takes only that entry off. A new terminal runs `stagepack-studio`, which finds the `.com`; an AI assistant's MCP command can be `stagepack-studio.com`. Not yet run on Windows: hand checks 4 to 6, 13 and 14.
  - Is a 561 MB install, 150 MiB download acceptable? Nearly all of it is the compiler bundle.
  - **Should the Linux build need an older glibc?** *Answered (plan E2): yes, 2.35.* `scripts/package-linux.sh` builds the release, the bundle's proc-macro libraries and the package in an Ubuntu 22.04 container (`stagepack-studio-build:22.04`), and `package glibc-check` then checks every ELF file in the package against 2.35. On 2026-11-24 the highest need was 2.35 (`stagepack-studio`); `stagepack-terminal` and the two proc-macro libraries need 2.34, and the toolchain's `rustc`, `librustc_driver`, `libLLVM` and `rust-lld` 2.17 or lower. The ignored test `old_systems` installs the package in `ubuntu:22.04` and `debian:12` containers, runs `help` and `check` on a talk with components, and uninstalls. RHEL 9 (glibc 2.34) is still out. `install.sh` still refuses, with the reason, where it can't start.
  - **Should uninstalling on Windows give the earlier default for `.sptx` back?** *Answered (plan E2): yes.* Installing saves the earlier default's ProgID in `HKCU\Software\Stagepack Studio` (`PreviousSptxDefault`; never our own, so a reinstall keeps the earlier one). Uninstalling makes it the default again if `.sptx` then has no default and the ProgID still exists under `HKCU\Software\Classes` or `HKCR`, and deletes that key either way. Not yet run on Windows: hand checks 13 and 14.
- **The Windows exe has no embedded icon yet.** The installer, the Start menu entry and the uninstall list use the `.ico`, but Explorer shows the exe with a plain icon until a resource step is added (it can't be checked here).
- **Licence texts:** the standard texts for 0BSD, Zlib, BSD-3-Clause and Unlicense aren't in the toolchain's folder, so a crate with one of those and no licence file gets its expression and a line saying no file came with it; `standard_text` reruns `rustc` for each id (slow, harmless); the `rust-src` fallback for the toolchain's notices is untested.
- **Staging:** the size check uses the size on disk, not the apparent size; there's no test that the folder holds nothing extra beyond the layout; the string `STUDIO_TERMINAL_HELPER` is still in a shipped binary (it isn't read).
- **Linux scripts:** a `SIGKILL` in the middle of a copy leaves a `stagepack-studio.new-<pid>` folder beside the app folder (the next install sweeps only our own); uninstalling leaves empty folders and rebuilt desktop and MIME caches, not removing what we didn't create.
- **Windows scripts:** `repo_root()` on a UNC path isn't handled. `scripts/test-all.ps1` leaves out the Linux package's tests (they need `bash` and `zstd`) and has never run; its `-Quick` skips the release step and the staged-app test. `make-bundle.ps1` builds the proc-macro DLLs with the C runtime linked in through cargo's `-Zhost-config`, which a stable toolchain allows only under `RUSTC_BOOTSTRAP=1` (set for that one build): under `--target` cargo passes host builds no rust flags otherwise. Checked here on Linux with a scratch crate (the host flag reached the proc-macro and not the wasm build); not run on Windows.
- **The test scripts:** a rerun of the release step builds the whole workspace in release (about 25 minutes here) where one target would do; a failing step still ends the script with status 1 even when its rerun passed (the summary says both).

## Hand checks for the owner

On Windows, from a fresh clone, with PowerShell (none of this has run):

0. **The scripts first.** In PowerShell run `scripts\test-all.ps1 -List`, then `scripts\test-all.ps1 -Quick`, before anything else: neither PowerShell script has ever run, and a failure here is a fix round.
1. **Build at all.** The Windows code in the app, the helper and the console twin has never been compiled. Install Rust (with `x86_64-pc-windows-msvc` and `wasm32-unknown-unknown`) and **Inno Setup 6.3 or newer**, then run `scripts\package-windows.ps1`. It runs `scripts\test-all.ps1 -Quick` first. Compile errors, a failing test, a stage over 600 MB or an Inno error come back as a fix round; they are expected, not a surprise.
2. `target\package\stagepack-studio-0.1.0-windows-x86_64-setup.exe` is made. In a Developer PowerShell, run `dumpbin /dependents` on each `.exe`, `.com` and `.dll` in `target\package-stage`: our three programs and the proc-macro DLLs in `bundle\toolkit\deps` list no `VCRUNTIME140.dll`. Note what the files in `bundle\bin` (rustup's `rustc.exe` and its DLLs) list: if they need it too, the runtime has to ship beside them, which is a fix round. **Run the first install in Windows Sandbox** (or a clean VM), whose image has no Visual C++ runtime: the app starts and a component builds; a fresh user on your own PC would pass even if the runtime were missing, since the Build Tools installed it for everyone. Then install it under a **fresh Windows user with no Rust and no admin rights**. No password is asked, nothing needs the internet, and it installs under `%LOCALAPPDATA%\Programs\Stagepack Studio`.
3. Before installing, run `reg query HKCU\Software\Classes\.sptx /s` and keep the output (it shows what Stagepack, or anything else, registered). Double-click a `.sptx` file: it opens in Stagepack Studio, with no console window. Right-click, *Open with*: Stagepack Studio is listed, and so is any other program that was there before. `reg query HKCU\Software\Classes\.sptx /s` again: the earlier default's ProgID is now under `OpenWithProgids`. (If you once chose a program for `.sptx` with *Always*, Windows keeps that choice over ours; that is Windows policy.)
4. Before installing, also run `reg query HKCU\Environment /v Path` and keep the output.
5. After installing, a new terminal runs `stagepack-studio help`, and `reg query HKCU\Environment /v Path` shows the app's folder once, at the end, with the other entries as before and the type `REG_EXPAND_SZ` (entries such as `%USERPROFILE%\...` stay written that way). Also try a user with no `Path` value at all (`reg delete HKCU\Environment /v Path` on a scratch user): afterwards `Path` is just the folder, with no leading `;`.
6. `where stagepack-studio` lists the `.com` first.
7. **The no-code success test, step by step** (design's first success test): from the Start menu open Stagepack Studio, start from a template, add slides, a picture, a chart and a table with the mouse, save it as a packed talk, export to PowerPoint and open the `.pptx` in desktop PowerPoint, and present it with F5 and the presenter's view. You never see a terminal or type code.
8. **The coder success test:** with the guide (`stagepack-studio.com guide`, or the installed `guide` folder), write a talk's own component in a `components` folder, build it from the app (the compiler bundle is the installed one; no Rust is on the machine), and see it on the slide. **No console window flashes up** while it builds.
9. **Commands:** in a new PowerShell, `stagepack-studio help`, `stagepack-studio check <talk>` and `stagepack-studio outline <talk>` from any folder print in the terminal and set the exit code (`$LASTEXITCODE`); the console twin `stagepack-studio.com` waits for the command to finish.
10. **The AI tool's `mcp` from PowerShell:** the assistant's MCP command is `stagepack-studio.com` with `mcp <talk>`; check it answers (and with the full path of `stagepack-studio.com` too).
11. **The live terminal with `powershell.exe`:** a slide with `<Terminal run="powershell.exe" … />` asks *Run*, starts, takes typing and ends with the show (see plan G5's Windows list for the rest). The helper is `stagepack-terminal.exe` beside the app.
12. The setup upgrades over an older install of the same program and keeps the data folder. Also upgrade from a build whose bundle came from a different Rust version: a component still builds (the old `bundle` folder is removed first).
13. **Reinstall** the same setup over itself: `Path` still holds the folder once, and `reg query "HKCU\Software\Stagepack Studio"` still holds the earlier program's ProgID as `PreviousSptxDefault`, not ours (`StagepackStudio.Talk`). (If nothing else was the default before the first install, the key isn't there.)
14. **Uninstall** from *Installed apps*: the app's folder goes, the Start menu entry goes, `.sptx` is no longer ours, and **`%APPDATA%\stagepack-studio` is still there**. The program that was the default before stays under *Open with* and is the default again if it is still installed; `reg query HKCU\Software\Classes\.sptx /s` shows its ProgID as the default and still under `OpenWithProgids`, and our `StagepackStudio.Talk` gone. If that program was uninstalled first, `.sptx` has no default. `reg query HKCU\Environment /v Path` shows the same entries as in item 4, in the same order and written the same way (`%USERPROFILE%\...` unexpanded), without the app's folder. Two things may differ: empty entries are gone (such as the trailing `;` a new user's `Path` often has), and the type is `REG_EXPAND_SZ` even if it was `REG_SZ`. A user who had no `Path` has none again, and `HKCU\Software\Stagepack Studio` is gone.
15. The exe's icon in Explorer: expected to be plain (no embedded icon yet).

On Linux, with the tarball, under a fresh user (or a scratch home) on a real desktop:

1. `tar --use-compress-program=zstd -xf stagepack-studio-0.1.0-linux-x86_64.tar.zst` and `sh stagepack-studio-0.1.0/install.sh`. No password, nothing outside the home.
2. The menu entry *Stagepack Studio* appears, with its icon; it starts the app with no Rust installed.
3. Double-click a `.sptx` in the file manager: it opens in Stagepack Studio, also with Stagepack installed; *Open with* still lists Stagepack and any other program that opens the type. After `uninstall.sh` it opens in Stagepack again.
4. Both success tests as above (the no-code one with LibreOffice or another viewer for the `.pptx` if PowerPoint isn't there; the coder one with a component from the guide).
5. `stagepack-studio help`, `check` and `mcp` from a terminal (with `~/.local/bin` on the `PATH`).
6. A live terminal with `bash`, asking first.
7. Install again over the same version and over an older one, with the app running: nothing in `~/.local/share/stagepack-studio` changes, and the installer says to restart the running copy. `uninstall.sh` takes away the folder, the link, the entry, the type and the icons and puts back any default it replaced, and leaves the data folder.

## The final review

A whole-branch review of `7cb9521..db30a4d` on the most capable model found that the packaging could merge with fixes: 1 critical, 5 important and 8 minor findings. One fix wave (`2889bbb`, `92b2b9e`, `37ae3b2`, `9365060`, `1df84ef`) and one controller fix (`76eaaa6`) answered them; a re-review on the same model passed them, apart from the minor points parked below.

- **Critical: `.sptx` on Linux where Stagepack is installed.** Stagepack registers its own type for the files, `application/x-stagepack`, with a glob of weight 90, so files never took our type and Stagepack Studio wasn't even under *Open with*. Our entry now lists Stagepack's type as well and is the default for both. The default each type had is recorded per list and given back on uninstall. Our glob keeps the default weight: the fix wave first raised it to 90, which tied with Stagepack's, and the tie made the files ours and dropped Stagepack from *Open with*. The re-review caught this, and the controller fixed it. The test now uses a faithful copy of Stagepack's registration; it fails at weight 90 and passes at the default.
- **Important, Windows:**
  - an upgrade clears `{app}\bundle` first, so a new toolchain's libraries never sit beside the old ones;
  - component builds start `rustc` with no console window;
  - the three programs are built with the C runtime linked in, and so are the bundle's proc-macro DLLs;
  - the earlier program for `.sptx` stays under *Open with*.
- **Important, Linux:** `install.sh` runs the new copy before the swap and refuses, with the loader's message, where it can't start (it needed glibc 2.39 or later then; 2.35 since plan E2).
- **Minor:** messages after the swap; a note to restart a running copy; the zip subclass and generic icon; a stricter `stage` guard; `STUDIO_BUNDLE` restored after the components rerun in `test-all.ps1`; nested scripts run with `-ExecutionPolicy Bypass`; `test_all` always run on Windows, and skipping itself where `bash` can't run the script; this record's wording.
- **Parked for the Windows hand checks:**
  - `make-bundle.ps1` turns on `RUSTC_BOOTSTRAP` for the proc-macro build. That also enables proc-macro2's nightly-only code in those DLLs, and the script removes a value the caller had set. If `dumpbin` shows the bundle's `rustc` needs `VCRUNTIME140` anyway, shipping `vcruntime140.dll` and `vcruntime140_1.dll` in `bundle\bin` is the better fix, and the block goes.
  - Two Windows text tests could be stricter.
  - The `{reg:…}` entry reads only `HKCU`, so a machine-wide registration isn't kept under *Open with*.

Not done from the review's recommendations: staging into a path with a space and a non-ASCII letter, and building against an older glibc (an owner question above).
